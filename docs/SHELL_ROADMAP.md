# Oxibar Widget Shell Roadmap

## Goal and Scope

Evolve the existing Rust/Iced layer-shell daemon into a complete, plugin-driven
desktop widget shell. Keep the `oxibar` executable and Home Manager module
compatible while the product grows beyond a bar.

The shell owns bars, launchers, panels, control-center widgets, OSDs, a dock,
desktop widgets, settings, and session-action UI. The existing Wayland compositor
continues to own window management, composition, effects, and global keybindings.
Wallpaper display is an optional background surface/service. Locking remains an
integration with a dedicated locker, rather than treating a normal overlay as a
session lock.

Keep Iced, `iced_layershell`, and `oxiced`. Use Noctalia as UX inspiration:
consistent surfaces, a discoverable control center, immediate settings, and
per-monitor widget editing. Its implementation stack is not a dependency.

**Status:** milestone 0, milestone 1 and the initial GUI/settings slice of milestone
2 are implemented, plus the initial multi-output registry/inventory slice of
milestone 3 and milestone 4's control-center/native services/OSDs. Settings/control-center
surfaces use spacious Android-inspired grouping
with the existing oxiced theme. Milestone 5's dock and persistent desktop widgets
and milestone 6's live themes/providers are implemented. The release gate is next.
Shared `oxiced` now lives in this workspace.

## Starting Point

- One resident host already owns bar/popup/modal/panel/toast surfaces.
- Dynamic Rust plugins own models, subscriptions, updates, and inner views.
- Audio, battery, Bluetooth, clock/CalDAV, network, notifications, tray, and
  Hyprland workspaces already provide useful shell functionality.
- The application launcher now shares the host renderer. Applications are indexed
  in background workers, retained in memory, and exposed through optional runner
  hooks on the existing plugin API.
- Nix builds host and plugin packages from one pinned workspace dependency cache.
- Configuration uses immutable, source-aware snapshots and a serialized override
  store. The initial settings UI applies host geometry/layout and supported plugin
  fields live. Immutable theme snapshots apply palette/font/density/motion live;
  legacy bar font, lifecycle and backend timers retain restart classification.

## Configuration Contract: GUI Overrides Nix

The GUI must override effective Nix values without editing a Nix-store file or
replacing Home Manager's generated config symlink.

```text
compiled defaults
    < config.toml              # existing base; may be generated by Nix
    < overrides.toml           # writable, sparse GUI/user overrides
    < session preview          # temporary; only during an explicit preview
    = validated effective configuration + per-setting source
```

Both files live in `$XDG_CONFIG_HOME/oxibar/`. Preserve the existing
`programs.oxibar.config.plugin_config` interface as the declarative base. Add
typed Home Manager options gradually, mapping them to the same schema. Home
Manager installs plugin packages and manages only the base configuration, never
the GUI override file.

### Merge and Reset Semantics

- Recursively merge tables. Replace scalars and arrays as whole values; never
  concatenate bar ordering, plugin allow-lists, or monitor selections.
- Overrides contain only values the user explicitly changed. Do not serialize
  the entire effective config, which would freeze future Nix/default updates.
- Preserve an explicit override even if its value currently equals the base:
  source/intent must not change after a subsequent Nix rebuild.
- **Reset to Nix/default** removes that setting from the override layer, pruning
  empty parent tables. It does not copy today's base value into the override file.
- Empty arrays explicitly disable/empty a list. Use explicit `enabled = false`
  or schema-defined optional-value states for disabling a feature; TOML has no
  null/tombstone value.
- Keep the base snapshot separate from its default-expanded effective snapshot,
  so the UI can distinguish Built-in, Nix/base, and GUI sources.
- Unknown plugin tables and future fields must survive round trips. Validate
  known settings through host/plugin schemas without discarding unknown data.

Example:

```toml
# Nix-generated config.toml
[bar]
height = 31
center = ["clock"]

[launcher]
max_entries = 7
```

```toml
# GUI-written overrides.toml
[bar]
height = 38
```

If a rebuild changes base height to 34 and launcher limit to 10, effective height
remains 38 and launcher limit becomes 10. Resetting height reveals 34.

### Persistence and Reload

- Make the daemon the single settings writer; GUI and IPC changes go through
  typed commands and revision checks.
- Validate a candidate effective config before saving. Write a temporary sibling,
  flush/sync it, then atomically rename; surface persistence failures in the GUI.
- Watch containing directories as well as files so atomic edits and Home Manager
  symlink replacement are detected. Coalesce change events and ignore self-write
  echoes by revision/content identity.
- Retain the last valid snapshot on invalid external edits. Report field/path
  errors without bringing down the bar or overwriting the broken input.
- Classify each setting as live, surface-recreate, or restart-required. Changing
  widget order should be live; monitor/layer geometry may recreate surfaces;
  legacy plugin initialization and static-theme settings initially need restart.
- Convert bundled plugins to live config hooks incrementally. Do not unload a
  legacy dylib while its tasks, streams, threads, or Iced elements are alive.
- Plugin enable/disable changes select from installed libraries. A GUI toggle
  cannot install a missing Nix package; show availability separately from enablement.
- Offer effective-TOML export and override export; later add a Nix snippet export
  so users can promote chosen GUI settings back into declarative configuration.

## Target Boundaries

Grow along existing modules before introducing additional workspace crates:

| Boundary | Responsibility |
| --- | --- |
| `src/config/` | Typed host schema, base/override merge, validation, source tracking, persistence, reload |
| `src/shell/` | Surface registry, output routing, keyboard/focus policy, widget instances and interaction state |
| `src/ipc.rs` / future `src/ipc/` | Versioned control protocol and typed commands into the daemon |
| `src/settings/` | Iced settings screens and reusable schema-driven controls |
| `src/control_center.rs` | Host-owned provider selection, embedded controls and surface lifecycle |
| `src/services/` | Shared output/app/icon/session state and reusable system backends when several widgets need them |
| `crates/oxibar-plugin-api` | Existing exports plus optional settings, view-context, runner, desktop-widget, and lifecycle capabilities |
| `plugins/*` | Existing domain functionality, plugin-specific configuration and widget content |
| `crates/oxiced` | Local theme-aware shared controls; immutable theme snapshots remain future work |

`app.rs` remains the orchestration layer, delegating state transitions to these
modules. Avoid expanding it into a shell-wide god file. Extract a shared crate
only when both host and multiple plugins need a stable implementation/interface.

System state should have one cached owner per backend, with snapshots/events
feeding several views. Bar, control-center, desktop and OSD views must not start
independent copies of the same poller or DBus connection.

implementations and tested ideas, not as the shell's replacement architecture.

### Integration Method

1. Start with small adapters inside `plugins/audio`, `plugins/bluetooth` and
   `src/monitor/`. Keep their public plugin exports, current views, availability
   behavior, MPRIS controls and pairing/password flows. Move backend ownership
   into a shared service only when several independent consumers need it.
2. Port pure DTO conversion, geometry and state-reduction logic first, with
   provenance and focused fixtures. Introduce native dependencies through the
   existing pinned flake/workspace when each backend is implemented; do not make
   the entire `reset_daemon`/GTK dependency graph a launcher or shell prerequisite.
3. Use one native audio context and one BlueZ state owner, publishing snapshots
   and deltas into the existing plugin message flow. Native backend selection
   should coexist with the current CLI adapters until action/state parity is
   verified. An adapter to an already-running ReSet DBus service can be optional,
   but the shell must also work independently.
4. Establish cancellation, reconnect, resnapshot and bounded-channel behavior.
   Keep mainloops and DBus calls off Iced's update path. A dylib must own any
   runtime it requires; it cannot implicitly use host Tokio TLS. Do not copy
   `unwrap`-heavy parsing, disconnected-receiver loops or blocking async sleeps.
5. Start monitor reuse with read-only output inventory/capabilities for shell
   placement. Add an optional Iced display-settings plugin for resolution,
   refresh, scale, rotation and arrangement through compositor APIs. This is a
   settings client; composition/window management remain external.
6. Probe supported protocol versions/capabilities rather than relying only on
   desktop-environment strings. Preserve precise refresh rates and track Wayland
   events by protocol object identity; donor refresh-rate rounding and unsafe
   `Cell` Send/Sync shortcuts are not patterns to preserve. Validate Hyprland
   apply syntax against the supported compositor version rather than copying
   donor Lua/config snippets blindly.
7. Keep focused-output selection distinct from output-management inventory:
   the wlr output manager does not provide a generic focused-monitor query.
8. For display changes, distinguish Apply/preview/revert from saved desired
   profiles. Persist GUI profiles through the base/override settings service and
   use explicit runtime compositor calls or a dedicated user-owned exported
   include. Do not write generated compositor/Nix-store configuration files.
   KDE/GNOME adapters are further references, not a promise of layer-shell support
   on compositors that do not provide it.

**Reuse priority:** output inventory/geometry in milestone 3; native audio, BlueZ
and display-settings capabilities in milestone 4. First prove each adapter's
state/action parity before replacing its existing integration.

The initial audio adapter is implemented inside the existing plugin: one native
context/mainloop, sink/source/server events, cached device snapshots and default/
volume/mute actions. It uses thread-affine ownership, bounded commands and joined
cancellation rather than the donor's threaded callback borrowing. Private-server
and packaged GUI parity/reconnect checks pass. Profiles/streams and incremental
per-object queries remain later extensions.

The BlueZ adapter is also implemented inside the existing plugin: initial
ObjectManager state, incremental interface/property events, unique-owner epochs,
owned discovery, power/connect/trust/remove and complete Agent1 pairing. Typed UI
replies, full-flow cancellation and reconnect replace the donor's placeholders and
the old CLI pairing flow. Private injectable-bus and packaged GUI fixtures prove
parity without claiming global default-agent ownership or touching real hardware.

**Regression cases:** audio-server reconnect, removed defaults, card/profile and
per-stream updates; multiple adapters, property invalidation, cancelled pairing
and discovery stop; output hotplug, fractional scale/rotation, protocol event
ordering, unsupported feature flags and temporary display rollback. Borrow donor
fixtures where useful, rebuilding their tests against Oxibar's current API.

## Plugin Compatibility Contract

1. Keep current required exports, availability gates, allow-list ordering,
   error queues, subscriptions, and popup/modal/panel/toast requests.
2. Add optional capabilities rather than requiring every bar plugin to become
   a shell widget. The runner hooks already demonstrate this approach.
3. Add a declarative settings schema and optional config-change hook. The host
   renders common controls; an optional plugin settings view handles specialized
   editors. Keep unsupported legacy settings editable with a restart indicator.
4. Introduce stable widget-instance IDs separate from plugin IDs. Default old
   configurations still map to one instance per listed plugin.
5. Add optional context-aware views carrying output, instance, effective settings,
   and theme snapshot. Existing `view(model)` remains the fallback.
6. Add optional control-center, desktop-widget, OSD and command capabilities.
   Use host-owned surface placement/chrome for all of them.
7. Add cancellable lifecycle support before implementing in-process plugin
   disable/reload. Until then persist the change and restart the daemon normally.
   Optional `modal_closed` cleanup is implemented for task-modal retirement; it is
   not a general dylib unload/reload capability.
8. Continue building native plugins with the same pinned Rust/Iced/API graph.
   Version-gate breaking signatures; do not claim a stable cross-toolchain C ABI.

An optional capability addition need not bump today's ABI version. Breaking
changes to existing signatures or cross-boundary layouts do. Keep real dylib
regression tests alongside fake-plugin host tests.

## Milestones and Acceptance Criteria

### 0. Resident Launcher — Implemented

- `oxibar launcher [toggle|open|close]` controls an overlay in the running daemon.
- `applications` is a separately packaged plugin, enabled by Home Manager's
  default plugin set. Existing `[applications]` terminal/result-limit settings
  have equivalents; the legacy OxiRun ABI is ported, not loaded directly.
- Keep indexing and search off the Iced update thread; ignore stale query results.
- Globally rank bounded results while retaining each provider's local launch ID.
- Activation and Escape close only the launcher surface.

Verified with workspace tests, strict Clippy, Nix host/applications/clock builds,
a real dylib test without a host Tokio reactor, and a Hyprland typed-search/
launch smoke test. See `DECISIONS.md` for measured warm configuration latency.

### 1. Settings Foundation — Implemented

**Depends on:** milestone 0.

- Replace startup-only configuration access with immutable effective snapshots.
- Implement the base/override/source contract above with a typed schema for bar,
  launcher, surfaces and plugin enablement. Keep plugin raw tables compatible.
- Add a settings command boundary and versioned IPC responses, including state,
  errors and config revisions rather than only queue acknowledgement.
- Add schema/config-change capabilities to the plugin API without forcing legacy
  plugin unloads. Start with the launcher provider and simple bundled plugins.
- Use XDG-aware Home Manager installation paths for plugin libraries as well as
  base config.

**Acceptance:** a GUI-equivalent command changes one field; restart preserves it;
a Nix-base replacement changes unoverridden fields; reset reveals the new base;
arrays replace correctly; invalid files and interrupted writes retain valid state.
Existing config and plugin tests still pass.

Implemented with typed/source-aware snapshots, atomic sparse persistence, path-
replacement reload, versioned commands, optional schemas/hooks and XDG-aware Nix
installation. Revision/merge/invalid-input tests and packaged runtime smoke pass.

### 2. GUI Settings — Initial Slice Implemented, P0

**Depends on:** milestone 1.

- Add a host-owned settings window/panel with Appearance, Bar/Layout, Launcher,
  Notifications, Plugins, Monitor/Surface and Advanced categories.
- Search settings; expose current value, base value, source badge, reset action,
  validation error and live/restart status.
- Provide typed controls for booleans, ranges, enums, colors, commands, output
  selection and ordered widget lists. Reuse `oxiced` controls.
- Add widget add/remove/reorder UI and plugin availability/status diagnostics.
- Apply previewable changes immediately, debounce continuous edits, and persist
  accepted changes. Include a clear reset-all-overrides action.
- Open settings from a bar control, the launcher, the control center and IPC.

**Acceptance:** change bar height/order and launcher preferences without a Nix
rebuild; changes survive daemon restart and `home-manager switch`; individual
reset works; keyboard navigation is complete; restart-only settings are explicit.

Current UI includes Appearance, Bar/Layout, Launcher, Plugins, Advanced, Monitors
and Control Center pages, global search, source/reset controls, widget ordering,
installed-library status, typed plugin fields and sparse TOML editing. It opens
from bar, launcher, control center or IPC. Spacious oxiced cards/actions/switches
and responsive sidebar/picker navigation retain the existing theme.
Keyboard search, field traversal, Enter application, category shortcuts and Escape
are supported. Further palette/preset/display-control settings follow their
dependent milestones; generic button/switch keyboard accessibility remains a
shared-control follow-up.

### 3. Multi-output Shell Host — Initial Slice Implemented, P1

**Depends on:** milestone 1; can develop alongside milestone 2 once schema is fixed.

- Introduce a surface registry with explicit kinds, output IDs and window IDs;
  remove “unknown window means main bar” routing assumptions.
- Support multiple bar instances in one daemon, per-output placement, hotplug,
  output fallback and scale-aware geometry. Retain one shared plugin/service model
  unless a plugin explicitly needs per-instance state.
- Generalize modal/panel/overlay geometry and compositor backends beyond toast
  focus lookup. Add Hyprland first, then a second backend such as Niri/Sway;
  unsupported operations should have a defined fallback.
- Adapt ReSet's output DTO/geometry and capability ideas into the output registry;
  keep read-only inventory separate from optional display configuration.
- Centralize focus ownership, dismiss/restore behavior and input regions. Small
  shell surfaces must never leave invisible click-blocking areas behind.

**Acceptance:** hotplug/reconfigure outputs while bar, launcher, panels and
notifications remain correctly routed; Escape affects only the active overlay;
disabled/hidden surfaces release input and keyboard focus.

Implemented: explicit registered surface IDs, per-output top/bottom bars and
profiles, source-aware popup/modal/panel routing, hotplug reconciliation, shared
plugin state/subscriptions, optional context-aware views, read-only Hyprland and
generic Wayland inventories, and monitor UI/IPC diagnostics. Tests and three-
output/headless-hotplug smoke pass. Event-driven inventory and additional global-
focus adapters remain follow-ups; current refresh is background/coalesced polling.

### 4. Control Center and OSD — Implemented

**Depends on:** milestones 2 and 3.

- Compose a control-center panel from current audio, network, Bluetooth, battery,
  media, calendar and notification plugin capabilities.
- Preserve pairing/password modals, CalDAV, notification actions/replies, DND,
  tray menus and workspace dispatch; add reusable content views rather than
  duplicating or deleting these features.
- Add brightness and power-profile backends, session actions and volume/
  brightness/media OSDs through small additional plugins/services.
- Prefer event-driven DBus/sysfs backends and cached snapshots where they reduce
  repeated CLI polling; migrate integrations one backend at a time.
- Use the selective ReSet workstream above for native audio and BlueZ adapters,
  richer per-application audio/profile controls, and an optional display settings
  plugin. Verify existing actions and pairing behavior before backend replacement.

**Acceptance:** the same state updates bar, panel and OSD consistently; one
subscription/poller per domain; feature/availability fallback is visible; existing
interactive plugin flows remain usable.

Implemented: host-owned control center with optional dedicated views and legacy
popup/panel fallbacks, ordered provider tiles, shared models/subscriptions, scoped
keyboard navigation, live configuration, output ownership and retained async modal
routing. Audio/network/Bluetooth/battery/notifications have embedded views; calendar
uses its existing popup. Viewing the inbox suppresses toasts while retaining stored
notifications. Tests and a private-bus packaged compositor scenario pass, including
roomy/narrow layouts and repeated reopen.

Native audio now provides event-driven devices, defaults, balanced volume and
mute actions with cancellable/reconnecting ownership. MPRIS uses independent
bounded asynchronous queries/actions; explicit `pactl` compatibility remains.
Private PulseAudio and packaged GUI fixtures prove native actions, hotplug,
reconnect, media preservation and no native `pactl` calls. Native BlueZ now provides
cached adapter/device events, owned discovery and complete cancellable pairing;
private fixtures verify typed agent replies, modal cleanup, hotplug/reconnect and
zero `bluetoothctl` calls. System now adds cached backlights, modern/legacy power
profiles and verified login1 session capabilities, confirmation actions and a
dedicated-locker launch. Read-only OSDs coalesce per output, preserve action source
and release input/focus. Resident commands report actual outcomes without blocking
fast IPC. Private System/Audio/GUI fixtures pass, including keyboard input through
OSDs, domain failures, foreign-session rejection and source routing. Richer native
capabilities and optional display settings remain extensions.

### 5. Dock and Desktop Widgets — Implemented

**Depends on:** milestones 2–4.

- Add a dock with pinned apps, running-window indicators, activation and optional
  auto-hide. Share the resident application/icon index and use compositor adapters
  for running-window state; the dock does not manage window placement.
- Add host-owned desktop widget surfaces with stable instance IDs and per-output
  positions/sizes. Start with clock/calendar, media and lightweight system stats;
  weather is an optional provider with configurable refresh.
- Add explicit edit mode: add/remove, drag/resize, grid snap, reset placement.
  Store positions in logical/output-relative coordinates and define output-removal
  fallback. Outside edit mode, only actual interactive widget regions take input.
- Expose these capabilities to third-party plugins through optional hooks.

**Acceptance:** add two instances of one widget; move/resize and restart; hotplug
does not lose layout; desktop input remains usable; hidden widgets do not render
continuously or start duplicate system pollers.

The dock shares Applications' stable catalog and one host compositor broker.
Clock/calendar, media, battery and Stats expose reusable desktop content. Logical
layout drafts support add/remove/hide/output assignment, captured-coordinate
drag/resize, grid snap, reset and revision-safe persistence. Passive views can pass
input through; Clock/Stats pause their one owned stream when no consumer remains.
Private compositor checks passed exact launch/window activation, two-instance
editing, restart/hotplug, unknown fields, stale edits and hidden-view ownership.

### 6. Unified Theme and Launcher Providers — Implemented

**Depends on:** milestones 2–5 and context-aware plugin views.

- Refactor `oxiced`'s static global palette into immutable theme snapshots that
  host and upgraded plugins receive explicitly. Keep a legacy fallback while
  old plugins migrate; do not mutate unsynchronized globals across dylibs.
- Add live palette/font/density/animation preferences, reduced-motion support,
  presets and optional wallpaper-derived color generation.
- Extend launcher providers with commands, calculator, clipboard history,
  files/bookmarks and shell actions. Reuse suitable Oxi project functionality
  after reviewing its ABI, data ownership and resource lifecycle.
- Add provider prefixes, explicit actions, usage/favorites ranking, result status,
  locale-aware desktop entries, icon-theme inheritance and filesystem-driven
  index refresh. Coalesce/cancel stale work for larger datasets.

**Acceptance:** all upgraded surfaces change theme coherently without restart;
provider selection always routes one stable local action; query generations,
index updates and cancellation cannot execute a different displayed item.

Explicit immutable snapshots, live palette/font/density/presets/reduced motion and
legacy fallback are implemented. Applications adds localized actions, inherited
icons, filesystem updates and private usage/favorite ranking. Tools adds every
planned provider, including opt-in ephemeral native clipboard history. Prefixes,
captured immutable actions, pure validators and latest-only workers are verified
in source and isolated packaged GUI checks. Optional wallpaper-derived colors
remain an extension; the SDK/packaging/presentation-time gate follows.

### 7. Packaging, Plugin SDK and Release Gate — P2

**Depends on:** earlier functionality; apply verification continuously, not only here.

- Document optional capabilities, schemas, lifecycle rules and an example plugin;
  ship an installed-plugin catalog suitable for GUI enablement.
- Offer opt-in Home Manager user-service startup and compositor keybind examples.
  Keep packaged defaults immutable and GUI persistence outside Nix ownership.
- Keep launched applications outside the shell service's termination scope,
  using desktop activation or transient user scopes where available, so a shell
  restart does not terminate the user's applications.
- Preserve individually selectable plugin packages and shared Crane artifacts.
- Add repeatable compositor smoke scenarios for launcher/settings/input regions,
  multi-output changes and all existing modal/panel/toast flows.
- Measure release builds on a named reference machine: cold daemon initialization,
  warm first-presented-frame latency, query-to-results latency, idle CPU, wakeups
  and RSS growth after repeated open/close cycles.

**Targets:** warm overlay first frame p95 under 50 ms; bounded local-search results
within one 60 Hz frame for a documented reference index; no continuous rendering
while idle; idle CPU below 1% of one core on the reference setup; no monotonically
growing memory or worker count. The current configuration-time measurements are
not substitutes for presentation-time measurements.
